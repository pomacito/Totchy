# Специфікація rules engine

Реалізація: `src/lib/rules-engine/engine.ts` (чиста, детермінована функція без
side-effects і без звернень до БД — легко тестується) +
`src/lib/rules-engine/repository.ts` (шар доступу до даних, що готує вхід для
`engine.ts`).

## Вхід

```ts
type EngineInput = {
  targetUnit: TerritorialUnitDTO | null;
  ancestors: TerritorialUnitDTO[]; // батько → … → корінь, БЕЗ самого об'єкта
  candidateSourceVersions: SourceVersionDTO[]; // усі ОПУБЛІКОВАНІ редакції в системі
  records: StatusRecordDTO[]; // усі записи для targetUnit та ancestors, з усіх редакцій
  asOfDate: Date;
};
```

Захисний принцип: `engine.ts` НЕ довіряє повністю викликачу — записи, чий
`territorialUnitId` не належить `{targetUnit, ...ancestors}`, ігноруються
навіть якщо присутні у вхідному масиві `records` (знайдено і виправлено під
час написання тестів — див. `docs/DECISION_LOG.md` не потрібен окремий запис,
подробиці в коментарі коду `engine.ts`).

## Алгоритм (крок за кроком)

1. Якщо `targetUnit === null` → `UNIT_NOT_FOUND`. Використовується лише коли
   ідентифікація за кодом КАТОТТГ не дала результату — рушій сам нічого не
   "вгадує".
2. Побудувати адміністративний шлях (`administrativePath`) і позначити для
   кожної одиниці, чи існувала вона на `asOfDate` (`validFrom`/`validTo`).
3. **Обрати редакцію джерела для дати:** з `candidateSourceVersions` взяти
   найновішу (за `legalAct.effectiveAt`), чий `effectiveAt <= asOfDate`. Немає
   такої → `NO_REDACTION_FOR_DATE`. Це принципово ВІДРІЗНЯЄТЬСЯ від "статус не
   визначено" — означає лише, що жодна редакція документа ще не набрала
   чинності на цю дату.
4. Відфільтрувати `records` до тих, що (а) належать обраній редакції та (б)
   стосуються цільового об'єкта чи його предків (захисний фільтр, п. вище).
5. З відфільтрованих залишити чинні на `asOfDate`
   (`startDate <= asOfDate <= endDate`, або `endDate = null`).
   Немає жодного чинного запису → `FOUND_NO_RECORD`.
6. Серед чинних записів знайти максимальну "конкретність" рівня
   (`SETTLEMENT=4 > HROMADA=3 > RAION=2 > OBLAST=1`).
7. Якщо на цьому максимальному рівні кілька записів з РІЗНИМИ категоріями
   одночасно чинні → `NEEDS_REVIEW`. Рушій ніколи не обирає один із них
   довільно чи "за замовчуванням".
8. Інакше — єдиний запис максимальної конкретності визначає результат:
   `FOUND_STATUS`, з `appliesVia: "DIRECT"` (запис безпосередньо про об'єкт)
   або `"INHERITED"` (запис про одного з предків — найчастіше громаду).

## П'ять типів результату (навмисно різні, ніколи не змішуються)

| `outcome` | Значення | Коли |
|---|---|---|
| `UNIT_NOT_FOUND` | Об'єкт не ідентифіковано | немає такого КАТОТТГ у довіднику |
| `NO_REDACTION_FOR_DATE` | Немає застосовної редакції на дату | дата раніша за будь-яку чинну редакцію |
| `FOUND_NO_RECORD` | Об'єкт знайдено, запис відсутній | жоден запис (свій чи успадкований) не покриває дату |
| `NEEDS_REVIEW` | Конфлікт даних | кілька різних категорій одночасно на найконкретнішому рівні |
| `FOUND_STATUS` | Визначений статус | єдиний найконкретніший чинний запис |

Це прямо реалізує вимогу розділу 20 ТЗ: «Не приховуй помилки під загальним
статусом. Відрізняй: "не знайдено об'єкт", "об'єкт знайдено, запис у категорії
відсутній", "дані потребують перевірки", "джерело тимчасово недоступне"» —
`NO_REDACTION_FOR_DATE` відповідає ролі "джерело недоступне для цього періоду"
у межах rules engine; повна недоступність джерела в реальному часі (мережевий
збій під час імпорту) обробляється окремо в ETL-шарі (`ImportJob.status =
FAILED`), а вже опубліковані дані продовжують обслуговуватись (graceful
degradation, розділ 11 ТЗ).

## Тестове покриття

`tests/unit/rules-engine/engine.test.ts` (11 тестів, чисті fixture-об'єкти без
БД) покриває: усі 5 типів результату; пріоритет SETTLEMENT над HROMADA;
перехід DIRECT → INHERITED після завершення дії точкового запису і назад;
вибір різних редакцій для різних дат (версіювання в часі); захисний фільтр
проти нерелевантних записів.

`tests/integration/api.test.ts` (10 тестів проти реальної БД із seed-даними)
підтверджує ті самі сценарії через реальний HTTP-контракт API, включно з
омонімами (два "Ясенів" в різних областях) та відмінністю результату для
одного й того самого об'єкта до/після публікації нової редакції.
