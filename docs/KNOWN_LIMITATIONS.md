# Відомі обмеження цього MVP

Чесний перелік того, що свідомо не реалізовано або спрощено в межах цієї
ітерації, і чому. Нічого з переліченого не приховано — кожен пункт або показаний
в UI (банер/попередження), або задокументований у коді коментарем поруч із
відповідним місцем.

## Дані

- **Немає реального джерела даних.** Мережева політика цього середовища розробки
  блокує всі урядові домени (перевірено прямими спробами `WebFetch` перед
  початком роботи — `zakon.rada.gov.ua`, `data.gov.ua`, `mininfra.gov.ua`,
  `directory.org.ua`, навіть `uk.wikipedia.org`). Уся база — вигаданий
  демонстраційний набір із вигаданою географією (`isDemoData: true` на кожному
  записі, банер у кожному релевантному місці інтерфейсу).
- **Коди КАТОТТГ — спрощена демо-схема** (`DEMO-XX-XX-XX-TYPE`), не формат
  реального Кодифікатора. Поле в БД — звичайний рядок без апаратної прив'язки
  до конкретного формату, тож підключення реальних кодів не потребує зміни схеми.
- **Ретроспективна адміністративна ієрархія не моделюється.** Ланцюг
  "населений пункт → громада → район → область" будується за поточними
  зв'язками `parentId`, а не реконструюється на кожну історичну дату окремо
  (на відміну від записів статусу, які повністю темпоральні). Наслідок:
  історичний запит про об'єкт, чия адміністративна належність змінювалась
  внаслідок реформи, покаже поточну належність, а не ту, що діяла на обрану
  дату.

## Функціональність, винесена за межі цієї ітерації (друга черга)

- Інтерактивна карта (розділ 4.6 ТЗ).
- Email/web push підписки на зміну статусу — модель даних (`Subscription`)
  закладена в схему, доставка не реалізована.
- Формат звіту XLSX — реалізовано PDF і CSV; запит XLSX повертає явну помилку
  з поясненням, а не мовчазний XLSX-подібний CSV.
- PDF для звітів `COMPARISON`, `REGIONAL`, `ANALYTICS_PERIOD` — реалізовано CSV
  для всіх типів; PDF з повним оформленням (застереження, QR/URL перевірки)
  реалізовано лише для `SINGLE_TERRITORY`.

## Безпека та адміністрування

- **MFA для адміністративних ролей не реалізовано.** Сесія — HMAC-підписаний
  httpOnly cookie з паролем на `scrypt`; цього достатньо для демонстрації RBAC,
  але недостатньо для production-рівня захисту адміністративних дій.
- **Подвійне погодження критичних змін спрощене.** Rollback редакції вимагає
  одного явного підтвердження (`ADMIN` + обов'язковий коментар + `confirm:
  true`), а не незалежного підтвердження другою особою до виконання дії.
  Публікація нової редакції в цьому MVP теж виконується одним адміністратором
  через seed/адмін-панель, а не через двоступеневий workflow «підготовлено →
  підтверджено іншою особою → опубліковано».
- **Rate limiting — in-memory, не розподілений.** `checkRateLimit` рахує ліміти
  окремо на кожен процес; за горизонтального масштабування (кілька інстансів)
  ліміт де-факто множиться на кількість інстансів. Для production потрібен
  Redis-backed лічильник.

## Продуктивність

- **Аналітика обчислюється "з нуля" при кожному запиті** застосуванням rules
  engine до кожної звітної одиниці (`computeAnalyticsSummary`). Прийнятно для
  сотень одиниць демо-набору; для реального масштабу (десятки тисяч населених
  пунктів) потрібна матеріалізована проєкція, що оновлюється атомарно разом із
  публікацією нової редакції, а не обчислюється на льоту.
- **Звіти генеруються синхронно в межах HTTP-запиту**, без черги (Redis/BullMQ
  згадані в рекомендованій архітектурі ТЗ, але не підключені). Прийнятно для
  невеликих звітів MVP; великі звіти (наприклад, регіональний по всій області
  з тисячами записів) варто винести в чергу з окремим worker-процесом.
- **Об'єктне сховище — лише локальний диск** (`STORAGE_DRIVER=local`).
  S3-сумісний драйвер — явна заглушка з чіткою помилкою (`getStorageDriver`),
  а не мовчазний fallback.

## Доступність і UX

- Немає окремого автоматизованого accessibility-аудиту (axe-core тощо) —
  ручна перевірка базових вимог WCAG 2.2 AA виконана (клавіатурна навігація,
  видимий focus, ARIA-мітки, контраст, `prefers-reduced-motion`,
  колір ніколи не єдиний носій сенсу статусу), але без automated regression
  suite для доступності в CI.
- Немає повноцінних end-to-end тестів (Playwright test suite) — перевірка
  ключових сценаріїв виконана вручну через скріншоти під час розробки; каркас
  для e2e (`@playwright/test`) підключено як залежність, конкретні specs не
  написані в межах цієї ітерації.

## Залежності (dependency scanning)

`npm audit` (виконано під час розробки) показує відомі вразливості в `next`
(14.2.35 — найновіший патч на гілці 14.x, але частина GHSA-адвайзорі для
Next.js виправлена лише в мажорній версії 16.x), `postcss` (транзитивна
залежність через `next`) та `glob`/`@next/eslint-plugin-next` (транзитивні
залежності лінтера, не входять до production-бандла). Виправлення вимагає
`npm audit fix --force`, який оновлює Next.js на мажорну версію (14 → 16) —
це брейкінг-зміна App Router, яку свідомо НЕ виконано в межах цієї сесії, щоб
не дестабілізувати повністю протестований застосунок в останній момент без
можливості повторного регресійного тестування. **Перед production-запуском
обов'язково:** оновити Next.js до патченої версії в контрольованому релізі з
повним прогоном тестів і ручною перевіркою UI.

## Що потрібно зробити перед production-запуском

1. Підключити реальний парсер офіційного джерела замість `prisma/seed`.
2. Встановити `DEMO_DATA_MODE=false`, очистити демо-записи (`isDemoData=true`).
3. Додати MFA для ролей `ADMIN`/`LEGAL_VERIFIER`.
4. Замінити in-memory rate limiter на Redis-backed.
5. Підключити чергу для генерації звітів і S3-сумісне сховище.
6. Реалізувати XLSX та карту (модель даних вже сумісна).
7. Написати автоматизований a11y- та e2e-регрес.
