# Журнал рішень (Decision Log)

Цей документ фіксує ключові архітектурні та продуктові рішення, прийняті під час
розробки MVP системи «Статус території», разом з обґрунтуванням і зафіксованими
припущеннями там, де точна відповідь виходила за межі однієї сесії розробки.

## 1. Доступ до офіційних джерел

**Рішення.** Середовище розробки не має мережевого доступу до офіційних доменів
(`zakon.rada.gov.ua`, `data.gov.ua`, `mininfra.gov.ua`, `directory.org.ua`, навіть
`uk.wikipedia.org` — усі заблоковані політикою вихідного трафіку цього середовища,
що було перевірено прямими спробами `WebFetch` перед початком розробки).

**Наслідок.** Реалізовано повний вертикальний зріз (імпорт → БД → rules engine →
API → пошук → картка → звіт → тести) проти **вигаданого, чітко позначеного**
демонстраційного набору даних (`isDemoData: true` на кожному релевантному записі,
банер у кожному місці інтерфейсу, де показуються дані). Реальні географічні назви
навмисно НЕ використовуються для демо-даних (замість «Маріуполь» тощо — вигадані
«Вербівка», «Ясенів» тощо), щоб виключити навіть випадкову плутанину з реальним
статусом реальних територій. Це відповідає explicit fallback-правилу ТЗ (розділ 6,
20): «якщо немає доступу до актуального офіційного джерела, реалізуй адаптер і
fixture, чітко познач результат як демонстраційний».

**Що потрібно зробити перед production-використанням:** підключити реальний
парсер до офіційного джерела (структура ETL-конвеєра для цього вже закладена —
див. `import_jobs`, `validation_issues`, `source_versions` у схемі), замінити
демонстраційний seed на порожню БД, встановити `DEMO_DATA_MODE=false`.

## 2. Межі MVP цієї сесії

**Рішення.** Реалізовано функціональний вертикальний зріз відповідно до розділу 16
ТЗ. Явно ВИНЕСЕНО за межі цієї ітерації (задокументовано, не забуто):

- інтерактивна карта (розділ 4.6);
- email/web push підписки на зміну статусу (розділ 4.8) — модель даних
  (`Subscription`) закладена, доставка не реалізована;
- формат звіту XLSX — PDF і CSV реалізовано повністю;
- повноцінне подвійне погодження критичних змін (dual-control) — rollback
  вимагає одного підтвердження ADMIN з обов'язковим коментарем, а не незалежного
  підтвердження другою особою;
- MFA для адміністративних ролей;
- PDF для звітів COMPARISON / REGIONAL / ANALYTICS_PERIOD (реалізовано CSV;
  SINGLE_TERRITORY має і PDF, і CSV).

Це узгоджено з користувачем на початку сесії явним підтвердженням варіанту
«MVP vertical slice per section 16».

## 3. Технологічний стек

**Рішення.** Next.js 14 (App Router) + TypeScript (strict) + MUI v6 як наближення
Material Design 3 + PostgreSQL 16 (pg_trgm, unaccent) + Prisma ORM.

**Обґрунтування:**
- Next.js App Router дозволяє тримати rules engine, API-роути та UI в одному
  типобезпечному проєкті без окремого backend-сервісу — виправдано для MVP;
  REST API (App Router route handlers) обрано замість GraphQL, оскільки
  публічний контракт (розділ 10 ТЗ) явно описаний як набір REST-ендпоінтів
  з пагінацією/фільтрами, а не як граф сутностей з довільними вибірками.
- PostgreSQL + `pg_trgm` — достатньо для нечіткого пошуку на МVP-масштабі даних
  (розділ 9 explicitly дозволяє це для MVP, з міграцією на окремий пошуковий
  рушій лише за фактичної потреби).
- Prisma — типобезпечні міграції та явна тимчасова (effective-dated) модель.
- Немає окремого Python backend: ETL/парсинг для MVP реалізовано як
  TypeScript-модуль (`prisma/seed`), оскільки обсяг парсингу для демонстраційних
  фікстур не виправдовує окремий сервіс; за потреби парсер реальних офіційних
  документів можна винести в окремий воркер без зміни схеми даних.
- Черги (Redis/BullMQ): НЕ підключено в цьому MVP — звіти генеруються синхронно
  в межах HTTP-запиту (прийнятно для малих демонстраційних звітів; для реального
  масштабу документовано як необхідне вдосконалення в `KNOWN_LIMITATIONS.md`).
- M3: офіційної зрілої React-бібліотеки Material Design 3 не існує, тому M3
  реалізовано як набір рольових кольорових токенів і typography-правил поверх
  MUI (`src/theme/tokens.ts`, `createAppTheme.ts`) — компоненти MUI (Card, Chip,
  Dialog, TextField тощо) використані як реалізація M3-подібних компонентів.

## 4. Пріоритет рушія визначення статусу

**Рішення** (детально в `docs/RULES_ENGINE.md` і покрито тестами
`tests/unit/rules-engine/engine.test.ts`):

1. Для дати запиту обирається редакція джерела — найновіша ОПУБЛІКОВАНА
   редакція, чий нормативний акт набрав чинності не пізніше цієї дати.
   Немає такої редакції → `NO_REDACTION_FOR_DATE` (а не мовчазний "не знайдено").
2. У межах обраної редакції розглядаються лише записи, що стосуються самого
   об'єкта та його прямих адміністративних предків.
3. Серед чинних на дату записів перемагає найконкретніший рівень
   (SETTLEMENT > HROMADA > RAION > OBLAST).
4. Кілька записів з різними категоріями на однаковому найконкретнішому рівні →
   `NEEDS_REVIEW`, рушій не обирає один із них довільно.

Це власна, явно сформульована евристика (структурне рішення про пріоритет
рівня деталізації запису), а не витяг із конкретного нормативного тексту — вона
відповідає вимозі розділу 7 ТЗ «не вигадуй правило пріоритету… сформулюй його
після аналізу структури… зафіксуй у документації та покрий тестами».

## 5. Ретроспективна адміністративна ієрархія

**Прийняте припущення.** Ланцюг «населений пункт → громада → район → область»
для будь-якої дати запиту будується за ПОТОЧНОЮ ієрархією одиниць
(`TerritorialUnit.parentId`), а не реконструюється ретроспективно на кожну
конкретну історичну дату (адміністративно-територіальна реформа сама по собі
не моделюється в часі, на відміну від записів статусу, які повністю
темпоральні). Це задокументоване обмеження, а не помилка — зафіксовано в
`docs/KNOWN_LIMITATIONS.md` і на сторінці «Методологія».

## 6. Спрощена схема кодів КАТОТТГ у демо-наборі

**Рішення.** Оскільки реальний Кодифікатор недоступний (див. п.1), демо-дані
використовують явно вигадану схему кодів у форматі `DEMO-XX-XX-XX-TYPE`, яка
структурно нагадує ієрархію КАТОТТГ, але НІКОЛИ не видається за реальні коди
(префікс `DEMO-` унеможливлює плутанину). `TerritorialUnit.katottg` — звичайний
рядок без апаратної прив'язки до конкретного формату, тому реальні коди
КАТОТТГ (інший формат) підключаються без зміни схеми.

## 7. Автентифікація адміністративної панелі

**Рішення.** Власна легка сесійна модель (HMAC-підписаний httpOnly cookie,
`scrypt` для хешування паролів) замість зовнішньої auth-бібліотеки — виправдано
обсягом MVP (три ролі, без соціального входу, без MFA). RBAC (`EDITOR`,
`LEGAL_VERIFIER`, `ADMIN`) реалізовано на рівні кожного admin-ендпоінта.
MFA свідомо не реалізовано в цій ітерації — зафіксовано як відоме обмеження.

## 8. Шрифт для PDF-звітів

**Проблема, знайдена під час перевірки.** `@react-pdf/renderer` вимагає явно
зареєстрованого TTF-шрифту з кириличними гліфами — вбудований Helvetica їх не
містить. Початкова реалізація резолвила шлях до шрифту через `__dirname`, що
працювало локально, але не в зібраному Next.js-бандлі (бандлер не відстежує
файли, прочитані динамічно через `fs` у серверному коді, тому build не копіював
шрифти поруч із скомпільованим route-файлом — реальний production-бug, знайдений
і виправлений під час end-to-end перевірки). Виправлено: шрифти (DejaVu Sans,
дозволена ліцензія) перенесено в `public/fonts/` і читаються через
`path.join(process.cwd(), "public", "fonts", …)` — цей каталог детерміновано
копіюється і в `next start`, і в Docker-образ.
